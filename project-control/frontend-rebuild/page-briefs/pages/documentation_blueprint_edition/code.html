Understanding traceability

Traceability is the structural backbone of high-precision documentation. In DevDoc, it ensures that every line of code, every architectural decision, and every test case is directly wired back to a verified business objective. It prevents documentation drift by treating relationships as validated code.

The Anatomy of a Trace

A trace in DevDoc is not merely a hyperlink. It is a typed, bidirectional relationship enforced by the internal validation schema. When you reference a Business Objective like BO-01, the system verifies its status and automatically updates dependent Functional Requirements such as FR-12.

info

Bidirectional Updates

If an upstream artifact changes state (e.g., BO-01 moves from 'Approved' to 'Under Review'), all downstream artifacts connected via a "satisfies" trace will immediately be flagged by the Doc-Linter as 'Stale'.

Implementing Traces via Code

While traces can be created via the GUI, power users embed them directly into Markdown using our custom syntax block. This ensures that relationships are version-controlled alongside the content.

description authentication_flow.md 
---
title: "OAuth2 Authentication Flow"
type: "DESIGN_ELEMENT"
id: "DE-402"
traces:
  satisfies: ["FR-12", "SEC-05"]
  verified_by: ["TC-15"]
---

Handling Broken Traces

When an artifact is deleted or its ID changes, DevDoc's engine detects orphaned references. These appear as validation errors in your pipeline.

warning

Build Failure Risk

If strict mode is enabled in your `devdoc.config.yml`, broken traces will cause the documentation build to fail with a non-zero exit code. Always run the Doc-Linter locally before committing.
